# shogi-vs-cpu 設計

作成日: 2026-08-17

本ドキュメントは作成時点の設計ログである。実装が進んだ後に本ドキュメントを遡って更新はしない。最新の状態を表す正典はリポジトリの `README.md` および `CLAUDE.md`（実装セッションで作成）とする。

## 1. 概要

ブラウザで遊ぶ本将棋のCPU対戦ゲーム。ankardo（子供向けインディーゲームカタログ）のゲームの一つとして、独立リポジトリで開発し `ankardo.com/play/shogi-vs-cpu/*` に配信する。

### 確定した方針

| 項目 | 決定 |
|---|---|
| ルール | 本将棋フルルール（9×9、全駒、持ち駒、成り、打ち歩詰め禁止、詰み判定） |
| CPU | 自前TypeScriptによるαβ探索（外部WASMエンジンは使わない） |
| 描画 | DOM + CSS Grid（Canvas / Phaser は使わない） |
| 駒の表現 | 漢字表記 ＋ 選択時の合法手ハイライトで初心者を支援 |
| カタログのジャンル | `puzzle`（ankardo 側の `GENRES` は変更しない） |
| ビルド | Vite + 素の TypeScript（既存ゲームリポジトリの慣習に合わせる） |

### MVP に含む機能

- 本将棋フルルールの対局
- 難易度3段階（よわい / ふつう / つよい）
- 合法手ハイライト、最終手表示
- 待った（1手戻し）、投了、先手後手の選択
- 棋譜表示、localStorage による途中再開

## 2. アーキテクチャ

### レイヤと依存方向

依存は一方向のみで、逆流させない。

```
ui/          DOM描画・入力・画面遷移。core を読み、ai とは Worker 経由でのみやり取りする
  ↓
core/        将棋のルール。純粋関数のみ。DOM も Worker も timer も知らない
  ↑
ai/          探索。core の合法手生成を使う。Worker 内で動く
```

`core` を唯一の「正しさの源」とし、UI 側にルールの二重実装を作らない。UI のハイライトも AI の探索も、同じ合法手生成関数を呼ぶ。

### ディレクトリ構成

```text
shogi-vs-cpu/
├── index.html
├── vite.config.ts        base: '/play/shogi-vs-cpu/', outDir: 'out/play/shogi-vs-cpu'
├── vitest.config.ts
├── biome.json
├── wrangler.toml
├── .github/workflows/deploy.yml
├── src/
│   ├── core/             types, square, position, moves, rules, sfen, record
│   ├── ai/               evaluate, search, worker.ts
│   ├── ui/               board, hands, controls, record-view
│   ├── app/              ゲーム進行の統括（状態遷移、Worker 起動、保存/復元）
│   └── main.ts
└── docs/superpowers/specs/
```

### Worker 境界

メインスレッド ↔ Worker のメッセージは「局面（SFEN 文字列）＋難易度」を送り、「指し手」を受け取るだけに限定する。オブジェクトを直接渡さないため構造化クローンの制約を受けず、テストでは Worker を介さず探索関数を直接呼べる。

CPU 手番中は盤の入力を無効化し「かんがえちゅう」を表示する。弱いレベルで即着手して不自然にならないよう、最低思考時間（初期値 300ms）を設ける。

### ツールチェーン

- TypeScript strict（`noUnusedLocals` / `noUnusedParameters` を有効化。既存ゲームリポジトリと同じ）
- テスト: vitest
- lint / format: Biome（`sea-defence` の流儀に合わせる）
- ゲームライブラリは使わない。ランタイム依存ゼロ、依存は開発ツールのみ

## 3. ルール実装とデータ構造

### 盤の表現

`Int8Array(81)`。0 = 空、正の値 = 先手の駒、負の値 = 後手の駒、絶対値が駒種コード（歩1〜玉8、成駒9〜14）。探索中のオブジェクト割り当てを避けるための選択。テストの可読性は SFEN ⇄ 局面の変換ヘルパで担保する（テストは局面を SFEN 文字列で記述できる）。

マスは 0〜80 のインデックスで表し、`index = (段 - 1) * 9 + (9 - 筋)`。したがって index 0 は 9一。この変換は `core/square.ts` に閉じ込め、他モジュールで直接計算しない。

### 局面

```ts
{
  board: Int8Array,              // 81
  hands: [Int8Array, Int8Array], // 各7要素: 歩香桂銀金角飛
  sideToMove,
  ply
}
```

### 指し手

```ts
{ from: number | null, to: number, promote: boolean, drop?: PieceType }
```

`from === null` が打ち。ビット列へのパックはしない。深さ5・1局面あたり80手程度の規模では素の JS オブジェクトで足りるため、必要性が測定で示されるまで最適化しない。

### 合法手生成

疑似合法手を全て生成した後、自玉に王手がかかる手を除去する2段構え。速度より単純さを優先する。

この段階で扱う禁じ手:

- 二歩
- 行き所のない駒（1段目の歩・香、1〜2段目の桂）は生成しない（＝強制成り）
- 打ち歩詰め（歩を打った局面で相手が詰みなら非合法）

### 終局判定

- 詰み: 王手 かつ 合法手ゼロ
- 王手でない合法手ゼロも負けとして扱う
- 千日手: 同一局面4回で引き分け。連続王手の千日手は王手をかけ続けた側の負け
- 局面の同一性判定は SFEN 文字列をキーにした Map で数える（対局は数百手規模のため Zobrist ハッシュは不要）

### 非スコープ（意図的に実装しないもの）

- **入玉宣言法（27点法）**: 手数上限300手での引き分けで代替する。子供が CPU 相手に入玉将棋へ持ち込む確率に対し、実装とテストのコストが見合わない
- **CPU の投了**: 詰みまで指させる。子供が自分の手で詰ませられる体験を優先する
- 探索内部での千日手検出（対局レベルの判定のみ行う）

### 永続化と棋譜

- 局面のシリアライズは SFEN、棋譜は USI 形式の指し手列
- localStorage への保存と Worker 通信で同じ形式を使い回す
- 画面表示のみ日本語表記（▲7六歩、△3四歩、同、成、打）に変換する

## 4. AI（探索と難易度）

### 探索

αβ法 + 反復深化。深さ固定ではなく、持ち時間内に到達できた最深の結果を採用する。JS の指し手生成速度は実行環境による差が大きく、固定深さでは端末によって待ち時間が不安定になるため。

**静止探索（quiescence）は MVP に含める。** 将棋は駒の取り合いが連鎖するため、探索末端が取り合いの途中だと局面を誤評価する（水平線効果）。末端では取り返しの手のみを延長して評価する。これを省くと深さを増やしても CPU が駒をタダで捨てるため、削減できない。

### 評価関数

駒割 ＋ 持ち駒をやや高く評価 ＋ 玉周りの守り駒ボーナス。

駒割の初期値: 歩100 / 香300 / 桂320 / 銀520 / 金600 / 角800 / 飛950、成駒は加点。

駒の位置テーブルは導入しない。調整コストに対し、この強さ帯では駒割と静止探索の寄与が支配的なため。

### ムーブオーダリング

MVV-LVA（価値の高い駒を安い駒で取る手を優先）＋ 直前に良かった手を優先。αβ の枝刈り効率は実質ここで決まるため最低限入れる。

### 難易度3段階

| レベル | 探索 | ランダム性 |
|---|---|---|
| よわい | 深さ2固定・静止探索なし | 20%の確率で合法手からランダムに選ぶ |
| ふつう | 深さ3固定・静止探索あり | 最善から歩1枚分（100点）以内の手から選ぶ |
| つよい | 時間制限2秒の反復深化 | 同点手のみランダム |

**この表の数値は初期値であり、実際に遊んで調整する前提。**

「よわい」を単に深さを下げるだけにしないのは、駒割だけを見る探索は浅くても手堅く、子供がまず勝てないため。逆に完全ランダムでは対戦相手として成立しない。上記の混ぜ方で「時々ポカをする相手」にする。

同点手からのランダム選択は全レベルで行う。決定的だと毎回同一の対局になり、2局目以降の興味が失われるため。

### 非スコープ

定跡データベース、詰将棋専用ルーチン、置換表（Zobrist ハッシュ）。置換表は効果の大きい最適化だが、まず動くものを作って測定した後に判断する。

## 5. UI

### 画面

タイトル（難易度・先後の選択）→ 対局画面 → 終局モーダル、の3画面のみ。設定画面は作らない。

### レイアウト

スマホ縦持ちを優先し、上から「相手の駒台 / 9×9盤 / 自分の駒台 / 操作ボタン / 棋譜（折りたたみ）」の縦積み。盤は CSS Grid の `repeat(9, 1fr)` に `aspect-ratio: 1` を組み合わせて正方形を保ち、幅は画面幅から決める。デスクトップ・横持ちでは盤の横に棋譜パネルを置く2カラムへ切り替える。

### 駒

DOM 要素に漢字1文字を描画する（成香・成桂・成銀は縦2文字を縮小表示、と金は「と」）。後手の駒は `transform: rotate(180deg)`。画像アセットを使わないため、追加素材の準備を待たずに完成させられる。

### 操作フロー

1. 駒をタップ → 合法手のマスがハイライト
2. 行き先をタップで着手
3. 成れる場合のみ「成る / 成らない」のダイアログを表示。強制成り（1段目の歩・香、1〜2段目の桂）は確認せず自動で成る

持ち駒も同様に、タップ → 打てるマスがハイライト → 着手。選択中の駒を再度タップすると選択を解除する（誤タップから抜けられなくなることを防ぐ）。

### 盤面の状態表示

- 最終手の移動元・移動先をマーク
- 王手されている玉のマスを強調し「王手！」を表示
- CPU 手番中は「かんがえちゅう」表示＋入力無効化

### 操作ボタン

「まった」「とうりょう」「さいしょから」。投了は誤タップ防止のため確認を挟む。

### アクセシビリティ

- 81マスは `<button>` 要素とし、`aria-label` を「7六 歩」の形式にする。これによりキーボード操作とスクリーンリーダー対応が自然に得られる（DOM を選択した実利）
- ハイライトは色だけでなく枠線＋中央のドットでも表現する（色覚特性への配慮）
- タップ領域は最低 44px を確保する

### 文言

ボタンとメッセージは低学年でも読めるひらがな中心（「まった」「かんがえちゅう」「あなたの かち！」）。ただし駒の漢字と棋譜表記（▲7六歩）は本将棋のままとする。ここを崩すと実際の将棋を覚える助けにならないため。

### 非スコープ

駒の動き方を図解するヘルプ画面、効果音・BGM、演出アニメーション（駒の移動は CSS transition の最小限のみ）。

## 6. テスト戦略

`core` を主戦場とし、TDD で進める。

1. **合法手生成**: 駒種ごとの動き、飛角香の利きの遮蔽、成り、行き所のない駒、二歩、打ち歩詰め、王手放置、開き王手、合駒
2. **perft**: 指定深さまでの合法手の総数を数え、既知の値と照合する。個別ケースを積み上げても抜けは残るが、perft が既知値と一致すれば全ルールの組み合わせの正しさが保証される。深さ4までを CI に含め、深さ5はローカルで任意実行とする。**基準値は実装時に信頼できる出典で確認すること**（記憶に頼ると照合先の値自体を誤るため、本ドキュメントには値を記載しない）
3. **終局判定**: 詰み／詰みでない局面（逃げ道あり・合駒可能）、千日手、連続王手の千日手
4. **SFEN のラウンドトリップ**
5. **AI の回帰**: 1手詰めを必ず見つけること、駒をタダで捨てないこと（静止探索が壊れた場合に落ちるテスト）
6. **app 層の進行**: 対局開始 → 着手 → CPU応手 → 終局、待った、保存と復元。DOM に依存しない状態遷移として記述できる

UI の DOM 細部と E2E（Playwright）は非スコープ。1画面の静的ゲームであり、正しさの本体はユニットテストで守られるため。

## 7. デプロイとカタログ登録

ankardo の `new-game` スキル（`ankardo/.claude/skills/new-game/SKILL.md`）の手順に準拠する。

### ゲームリポジトリ側

- `vite.config.ts`: `base: '/play/shogi-vs-cpu/'`、`build.outDir: 'out/play/shogi-vs-cpu'`
  - Cloudflare Workers Static Assets はパス付きルートの場合、ビルド出力のディレクトリ構造自体が同じ階層にネストされていることを要求する
- `wrangler.toml`:
  - `name = "ankardo-game-shogi-vs-cpu"`
  - route: `ankardo.com/play/shogi-vs-cpu/*`（zone `ankardo.com`）
  - `assets.directory = "./out"`（ネスト前の出力ルート）
  - `not_found_handling = "404-page"`
- `wrangler` は `^4` を devDependencies に固定し、`actions/setup-node` は Node 22 以上
  - 3系にフォールバックすると、パス付きルート＋Assets のネスト構造がサポートされず deploy が失敗する既知の罠
- `.github/workflows/deploy.yml`: actions は SHA ピン、`environment: production`、`permissions: contents: read`、**test → build → deploy** の順

### Worker とベースパスの注意点

Worker は次の形で生成する。

```ts
new Worker(new URL('./worker.ts', import.meta.url), { type: 'module' })
```

この書き方であれば Vite が base path を含めて解決する。文字列パスで指定すると `/play/shogi-vs-cpu/` 配下で 404 になる。

### ankardo 側

`site/content/games/shogi-vs-cpu.json` を追加する。

```json
{
  "slug": "shogi-vs-cpu",
  "title": "しょうぎ どうじょう",
  "description": "コンピュータと対戦できる本将棋。強さは3段階から選べる。",
  "playUrl": "/play/shogi-vs-cpu/",
  "genre": "puzzle",
  "ageRange": "8歳〜",
  "players": "ひとり用",
  "difficulty": "むずかしめ"
}
```

`title` / `description` / `ageRange` / `difficulty` は案であり、公開前に調整してよい。

### 人手が必要な作業（エージェントが無承認で実行しない）

- `ankardo/scripts/setup-game-secrets.sh` の実行（Cloudflare 認証情報が必要）
- GitHub リポジトリの作成と `production` environment の保護ルール設定（必須レビュアー、`main` ブランチのみ許可）
- 実際の `wrangler deploy`
- ankardo 側 `site/` の再ビルド・デプロイと、カタログ一覧・詳細ページへの反映確認
